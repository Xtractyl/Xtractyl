# Local FHIR test server

One container sets this up automatically on `docker compose up`:

**`fhir_seed`** loads a fixed, reproducible set of synthetic FHIR bundles
into the `fhir` server. The bundles themselves are generated by a pinned
release of [Synthea](https://github.com/synthetichealth/synthea)
(`v4.0.0`) **at image build time** (`docker/fhir_seed/Dockerfile`, a
multi-stage build with a fixed `-s` seed and
`--exporter.fhir.use_us_core_ig=true`), not at container start — so the
dataset stays constant across `docker compose up` runs instead of
changing every time. This matters for drift comparisons, which need the
same underlying data across evaluation runs. The Synthea version is
pinned to a specific release tag rather than `master-branch-latest`, so
the generator itself doesn't silently change between builds either.

Regenerating the dataset (e.g. after bumping `FHIR_SYNTHEA_PATIENT_COUNT`
or `FHIR_SYNTHEA_SEED` in `.env`, or pinning a different Synthea release)
requires rebuilding `fhir_seed` **and** recreating `fhir` — rebuilding
`fhir_seed` alone leaves the already-running `fhir` container as-is, so
the newly seeded patients would just pile up next to the old ones instead
of replacing them:

```bash
docker compose down
docker compose up -d --build fhir_seed
```

(`down` removes `fhir` too, so it starts empty; `up --build` only forces
a rebuild of `fhir_seed`, everything else is a cache hit.)

`fhir` itself has no persistent volume — its data lives only in the
running container, so a full `docker compose down && up` always starts
from an empty server, and `fhir_seed` reloads the same fixed dataset into
it.

After `docker compose up`, the server is reachable at
`http://localhost:${FHIR_PORT:-8090}/fhir` (e.g.
`GET /fhir/DocumentReference`, `GET /fhir/Patient`).

API documentation (endpoints/schemas, not the stored data itself):
`http://localhost:${FHIR_PORT:-8090}/fhir/swagger-ui/`. Use its "Try it
out" on a `GET` operation, or `curl`/the URLs above, to see the actual
generated resources.

## Where the free text actually is

`DocumentReference.content[0].attachment.data` is base64-encoded and
holds the clinical note text:

```bash
curl -s "http://localhost:8090/fhir/DocumentReference?_count=1" | python3 -c "
import json, sys, base64
entry = json.load(sys.stdin)['entry'][0]['resource']
print(base64.b64decode(entry['content'][0]['attachment']['data']).decode('utf-8'))
"
```

Plain-structured text (markdown-style headings like `# Chief Complaint`,
not HTML/XML) — this is a candidate for the planned character-offset text
ingestion path, not the XPath/DOM path used for Docling-derived HTML.

`DiagnosticReport` without US Core enabled only covers structured lab
panels (no free text); the `conclusion` field is absent on those.
